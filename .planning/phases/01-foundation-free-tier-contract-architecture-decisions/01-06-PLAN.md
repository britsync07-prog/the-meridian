<objective>
Execute the five architecture-changing spikes — S-1 through S-5 — and record each outcome, the threshold it was measured against, and the decision it drove.

Purpose: These five questions each change the architecture, and each is cheap to answer now and expensive to answer later. S-1 decides whether a Durable Object can host the ingest engine on the free plan; S-2 and S-3 decide whether a Worker or a CI runner is the only viable fetch path; S-4 decides whether the static tier can hold topic and entity pages; S-5 decides what the deploy step costs. A spike that is not run leaves the architecture resting on an assumption, and an assumption that turns out to be wrong after the pipeline is built costs a rewrite. Recording the outcomes in the repository — rather than in a chat log — is what makes them usable as the Phase 2 and Phase 5 entry gates.

Output: Five runnable spike harnesses, five `RESULT.md` files with measured values, and `spikes/RESULTS.md` with one row per spike recording the metric, the observed value, the threshold, the decision and any resulting change to the delivery model.
</objective>

**S-1 — Durable Object CPU on Workers Free (30 minutes).** Question: does a Durable Object on the Free plan die at 10 ms CPU with `Error 1102`, or reach 30 seconds?

1. Create `spikes/s-1-do-cpu/wrangler.jsonc` with `name: "meridian-spike-s1"`, `main: "src/index.ts"`, `compatibility_date: "2026-10-20"`, `compatibility_flags: ["nodejs_compat"]`, and a `durable_objects` binding `{ "binding": "DO", "class_name": "CpuBurner" }` plus `migrations` for the new class.
2. Create `spikes/s-1-do-cpu/src/do.ts` — a Durable Object whose fetch handler burns CPU in a loop for a requested number of milliseconds (default 2000), accumulating a checksum so the loop cannot be optimised away, and returning `{ elapsedMs, checksum }`.
3. Create `spikes/s-1-do-cpu/src/index.ts` — a Worker that forwards the request to the Durable Object and returns its JSON, catching and reporting `Error 1102` if the runtime terminates the invocation.
4. Run it with `npx wrangler dev --config spikes/s-1-do-cpu/wrangler.jsonc`, then request `http://localhost:8787/?ms=2000`. Repeat with `?ms=100`.
5. Create `spikes/s-1-do-cpu/RESULT.md` recording: the observed maximum CPU milliseconds before termination, the error code if any (`Error 1102`), the wall time, and the decision — whether the Durable Object is a viable ingest engine on the Free plan. If the deployment path for a Durable Object is unavailable on the account, record that fact and the exact error, and state the decision as "the fetch-only Worker to R2 to CI default is confirmed", because either outcome leaves the default build intact.
